# 踩坑记录

> 这里每一条都是**实际踩到并修掉**的，不是"常见问题清单"。
> 格式：现象 → 根因 → 修法 → 教训。

---

## 1. 页眉页脚清理，把正文删了

- **现象**：入库后检索"单位"相关内容总是缺。检查发现 `单位：元 币种：人民币`、`√适用 □不适用`
  这类**正文行**被当成页眉页脚删掉了。
- **根因**：判定规则是"跨页高频出现的行就是页眉页脚"。但年报里有些正文行（单位声明、勾选框）
  本来就会在几十页里重复出现，被误判。
- **修法**：**只在每页的前 2 行与后 2 行**里做重复判定 —— 页眉页脚一定在版面边缘。
- **教训**：凡是用"统计规律"做内容清理，都要给它加一个**结构先验**（这里就是"位置"），
  否则规律强的地方一定误伤。

## 2. 页码抽不到 —— 它不在页脚

- **现象**：`printed_page` 几乎全是 `None`，正文里还残留 `60 / 143` 这种行。
- **根因**：我假设页码在页脚。实测**茅台在页首**（`60 / 143`）、**美的也在页首**（`- 59 -`），
  而"每页都不同的行"不会进重复行集合，所以既没抽走也没记录。
- **修法**：① 首尾都扫；② 收紧"纯数字"模式（必须带破折号），避免把表格里的孤立数字当页码；
  ③ 加一条兜底 —— 页首的**光秃数字**，只有在与 PDF 页序相差 ≤5 时才认。
- **教训**：**"我以为"是最贵的三个字。** 版面假设必须拿真实文件验证。

## 3. `usage` 是 SDK 对象，`json.dumps` 直接炸

- **现象**：流式结束时后端抛 `TypeError: Object of type CompletionUsage is not JSON serializable`，
  被兜成 error 事件；更糟的是前端拿到 error 会**覆盖已经流出的答案**。
- **根因**：`usage` 是 SDK 的对象，不是 dict，而 SSE 要 JSON 序列化。
- **修法**：加 `_usage_dict()` 转普通 dict；同时前端 error 分支改为"**有内容就追加，没内容才替换**"。
- **教训**：**跨层边界要显式转换**（对象 → 可序列化），并且**降级路径不能破坏已完成的工作**。

## 4. 流式下 `tool_calls` 是增量拼接的

- **现象**：工具调用第一次跑起来，函数名对但**参数是空的**。
- **根因**：流式响应里 `tool_calls` 分多个 chunk 陆续到达 —— 先给 `id` 和 `function.name`，
  参数是**一串碎片**。想当然地只读最后一次就只剩尾巴。
- **修法**：按 `index` 建槽位，把 `id` / `name` / `arguments` 分别累积，最后按 index 排序输出。
- **教训**：流式协议里**任何字段都可能是碎片**，必须自己拼。

## 5. 模型伪造引用：「片段 3」

- **现象**：多轮追问时，模型**一次检索都没做**，回答里却写着「（片段 3）」。
- **根因**：历史里上一轮的答案带着 `（片段 1、片段 2）`，模型在**照抄编号格式**。
- **修法**：三重。① 送模型前**剥掉历史里的引用标记**（引用编号只在本轮有效）；
  ② 提示词硬禁"本轮无片段时不得出现该字样"；③ **引用校验** —— 回答里的编号不在本轮 citations 里就报警。
- **教训**：**格式示范也是一种 Prompt。** 历史里出现过的模式，模型会当成模板模仿。

## 6. 模型跳过工具，凭记忆作答（软约束失效）

- **现象**：问「美的集团 2025 年营业收入是多少？」，模型**一次工具都没调**，
  还断言"美的尚未发布 2025 年报" —— 而语料里就有这份年报。
- **根因**：把检索做成"让模型自己调的工具"，就等于把 grounding 从**架构保证**降级成**提示词建议**。
- **修法**：先试提示词强化 —— **无效**。再上 `tool_choice="required"` 强制第一轮必须调工具 ——
  有效，但**调哪个工具仍由模型定**（它可能只调个 `calculate`，照样"调过了"）。
  最终方案是**双通道强制预取**：由代码取料并注入，模型只负责"基于资料作答"。
- **教训**：**能靠架构保证的，别交给提示词。** 提示词适合约束"表达"，不适合保证"事实"。

## 7. 模型的"思考过程"混进了答案

- **现象**：回答开头出现"我需要检索贵州茅台年报中关于销售渠道的描述。让我使用 search_knowledge 工具"。
- **根因**：工具调用轮里模型输出的叙述，被后端当成正文 `content` 流式推出了。
- **修法**：① 前端在收到 `tool_call` 时，把已有文字**挪进「思考」区**，与答案分离；
  ② 提示词加一条"调工具时直接调用，不要输出过程说明"。
- **教训**：**"给用户看的内容"与"过程日志"要分通道。** 前端能修的要修，别只指望模型闭嘴。

## 8. pandas 的科学计数法把模型带偏

- **现象**：财务数据返回的是 `4.451688e+10`，模型复述时位数出错。
- **根因**：`DataFrame.to_string()` 对大数默认用科学计数法。
- **修法**：改千分位格式化。
- **教训**：**给模型看的数字要"人话"**，否则它要额外做一次解析，出错面变大。

## 9. 10 倍单位换算错误

- **现象**：20 题评测里，模型把 `172,054,171,890.91 元` 写成「**172.05 亿元**」（应为 1720.5 亿元），
  把 `16,883,810.25 万元` 写成「**168.84 亿元**」（应为 1688.4 亿元）。
- **根因**：数字来源是对的，但**单位换算是模型心算的**。
- **修法**：**从源头消除** —— 结构化数据直接输出「原值 + 换算后」
  （`172,054,171,890.91 元（≈ 1,720.54 亿元）`）；注入块顶部再附一张单位换算参照表；
  提示词要求"凡换算必走 `calculate`"。
- **教训**：**别让模型做算术，哪怕只是移动小数点。** 能预先算好的一律预先算好。

## 10. 改了格式，把年度数据挤没了

- **现象**：为压缩长度，取数改成"只显示最近两期"。结果问「2025 年营收」时，
  通道 B 里**只有 2026Q2/Q1**，2025 年度数据不见了。
- **根因**：akshare 的列是**连续季度**（20260630 / 20260331 / 20251231 …），
  直接取前两列 ≠ 最近两个年度。
- **修法**：选期策略改为「**最新一期 + 最近两个以 `1231` 结尾的年度列**」。
- **教训**：**"最近"和"年度"是两个维度。** 改数据形态时要按真实使用场景验一遍。

## 11. 两个参数管同一件事，其中一个形同虚设

- **现象**：配置页能把"保留最近原文条数"改成 8，但**实际仍是 6**。
- **根因**：`memory_keep_recent`（配置页）和 `HISTORY_MAX_MESSAGES`（`.env`）都在管这件事，
  而上下文裁剪用的是后者，把前者**盖掉了**。
- **修法**：删掉 `.env` 那一项，`keep_recent` 成为唯一旋钮；同时给后端加**范围校验与钳制**。
- **教训**：**同一个概念只能有一个真相来源。** 重复的参数比错误的参数更伤信任。

## 12. 参数边界组合无解

- **现象**：给记忆参数加校验后，`keep_recent=40` 时"触发压缩阈值必须 > 保留条数"这条约束
  **永远无法满足**（两者上限都是 40）。
- **根因**：只在"每个参数各自合法"的层面想问题，没考虑**参数之间的关系约束**在边界处是否可满足。
- **修法**：把 `keep_recent` 上限压到 **30**（< `at` 的上限 40），保证 `at > keep` 始终可满足；
  并把"自动调整"的结果**回显给用户**（"已保存，但做了调整：…"）。
- **教训**：**校验要连"组合"一起想**，而且**静默改用户的输入是不可接受的**。

## 13. 加信息不总是好事 —— 要看加的是不是"有区分度"的信息

- **现象**：为了改善召回，给每个切块补上它在年报里的**章节路径**
  （如「公司简介和主要财务指标 › 联系人和联系方式」）再向量化 —— 覆盖率 99.5%，看起来很棒。
  结果：**recall@5 从 0.2208 掉到 0.2000，MRR 从 0.7679 掉到 0.7216**。
- **根因**：章节标题是**高频、低区分度**的文本。"重要提示、目录和释义""公司简介和主要财务指标"
  这类标题在几十上百块里反复出现 —— 拼进向量等于**给每块加噪声、把不同块拉近、稀释真正的内容语义**。
- **对照**：这跟另一个发现是**同一个现象** —— 「**去掉**公司名反而让召回变好」。
  公司名也是高频词，它会把整份年报的所有块一起拉高，盖住"资产负债率"这样的真实检索意图。
- **统一规律**：**embedding 对"高频、低区分度"的词很敏感 —— 它们稀释语义。**
  → 所以 Anthropic 的 Contextual Retrieval 有效，不是因为"加了上下文"，
  而是因为它加的是**chunk 专属、有区分度**的描述（"这段在讲美的 2025 年资产负债率"）。
- **教训**：**"加信息"不是优化，"加有区分度的信息"才是。** 加之前先问一句：这句话是不是到处都有？

## 14. 指标选错，会让你得出相反的结论

- **现象**：同一批实验数据，换一个指标，**最优配置从 A 变成了 E**。
  | 配置 | 旧指标 MRR | 新指标 金标命中@5 |
  |---|---|---|
  | ③ 关键词（去公司名） | **0.8604**（旧指标最高） | **0.5556**（新指标最低） |
  | ⑤ 去名关键词 + 重排 | 0.8000 | **0.7778**（新指标最高） |
- **根因**：旧口径把"**沾边也算相关**"的块全部计入分母 —— 有的题目池里有 **19–24 块**都算"相关"，
  于是 `recall@5` 的**理论上限只有 5/20 左右**，指标**结构性偏低**，量不出真实水平。
  而"去公司名"这个改动恰好会**召回一堆'主题沾边但没有答案'的块** —— 在旧指标下显得很好，
  实际是**把真正含答案的那块挤出了前 5**。
- **修法**：改用**金标块命中（Pass@k）** —— 每题只认 **1–2 块真正含答案的块**，看它有没有进前 k。
  这是业界常用口径（Anthropic 的 Contextual Retrieval cookbook 也这么测）。
  换过来之后，"重排有效"这个**真实优势**才显出来（它正是把金标块拉回来的那个动作）。
- **教训**：**先确认尺子量的是你要的东西，再谈优化。**
  指标选错时，你会**朝着错误方向调参**，还会把真实优势当成噪声。

## 15. 单靠一种标注源不可靠 —— 两级标注 + 人工裁定

- **现象**：检索评测的相关性标注（LLM 初标）看着挺合理，但做了次**盲审**就发现不对：
  请另一个独立子智能体（不给它原标注）重判同一批数据，**一致率只有 80%**。
- **根因（两方都错，双向噪声）**：
  - LLM 初标**偏松**：把"同一家公司的其他内容"（股权激励 vs 分红政策）也算相关；
  - 盲审**偏严**：明明写着"持续加大研发投入"的块也判不相关。
  - 而且盲审包我还**截断了片段**，导致个别片段的关键信息被截掉 → 制造了**假分歧**。
- **修法**：三级流水线 —— **① LLM 初标 → ② 独立盲审 → ③ 人工裁定分歧项**，
  把人工裁定当**金标准**回写标注。这次只改了 5 条，**配置排名就翻转了**（证明单源标注不足以支撑结论）。
- **教训**：
  1. **同源校验等于没校验** —— 让产出数据的那个流程去检查自己，只会自我确认；
  2. 盲审包**必须给全文**，截断会制造假分歧；
  3. **只有人工裁定那一步能当金标准**，LLM 的两轮都只是"候选"。

## 16. 改了代码默认值，行为却没变 —— 提示词在库里

- **现象**：调"回答太长"的问题，改了 `config.py` 里系统提示词第 7 条（加篇幅与禁止项），
  重启服务后再跑 —— **回答长度几乎没变**，看起来像"提示词没用"。
- **根因**：提示词的流向是**单向**的 ——
  ```
  首次启动：config.py ──写入──▶ app_config.system_prompt
  之后每次：       app_config.system_prompt ──读取──▶ 本轮对话
  ```
  **库里那一份才是"活的"**。已有部署的数据库里已经有行，改代码不会覆盖它。
  更绕的是：容器里的 `config.py` 也还是旧的（镜像在改代码之前构建的）—— **两处都旧**。
- **修法**：新增 `scripts/sync_prompt.py`（`--diff` 先看差异，不带参数则写入）；
  容器侧还要 `docker compose up -d --build` 重建镜像，否则镜像与仓库不一致。
- **教训**：
  1. **默认值与"当前生效值"是两回事** —— 有持久化配置时，改默认值 ≠ 改行为；
  2. **改了代码要问一句"它是从哪读的"**；
  3. 容器场景下还要多问一句"**镜像里的代码是哪一版**"。

## 17. 提示词"说了不听"？先问自己说得够不够具体

- **现象**：20 题评测里**对比类与多指标类回答要 22 秒**（标准 P95 < 20s）。拆解后：
  **首字只要 1.2s**，全部耗时都在生成阶段 —— **答案写到了 1095–1722 字**。
- **第一反应（错的）**：提示词第 7 条早就写着"回答**简洁直接**，不要长篇铺陈"——**模型根本没听**。
  所以第一版方案是"把输出上限从 1500 砍到 800"（用硬约束压）。
- **真正的根因**：那条规则**太抽象**。"简洁"是几个字？"长篇铺陈"算不算分点？
  模型无从判断，于是按自己的习惯写满。
  → **抽象的要求 ≈ 没有要求。**
- **修法（不动上限，只改措辞）**：把规则 7 从一句话改成可执行的具体约束：
  - 用「结论 + 要点」结构，分点写，**每点一句话**；
  - **篇幅：定性/数值类 ≤300 字；对比或多指标类 ≤500 字**；
  - **不要**复述问题、不要复述资料原文；
  - **不要**在结尾问"是否需要进一步分析 / 要不要我帮你查…"。
- **效果（20 题同条件重跑）**：

  | 指标 | 改前 | 改后 |
  |---|---|---|
  | 完成延迟 中位 / P95 | 10.02s / **22.6s ⚠️** | **7.64s / 9.97s ✅** |
  | 答案字数 中位 | 1095+（慢题） | **354** |
  | token 合计 | 95085 | **74613** |
  | 自动初判通过 | 20 / 20 | **20 / 20（未降）** |

  并人工抽查了 Q07 / Q10 / Q17 / Q18 的要点覆盖：**关键结论、数字、引用一个没丢**，
  反而更聚焦（Q10 还多出"四季度分项加总验算"）。**说明原来的长回答里确实一大半是废话。**
- **教训**：
  1. **"提示词没用"常常是"提示词不够具体"** —— 给字数、给结构、给禁止项，它才执行得动；
  2. **别一上来就上硬约束**（砍长度上限）。硬约束会**腰斩内容**，而这题的正解是**去废话**；
  3. **"完整"和"短"不冲突** —— 先去问"哪些字是必要的"，再问"怎么砍"；
  4. 硬上限（`MAX_OUTPUT_TOKENS`）该留，但它的职责是**防跑飞**，不是压缩工具。

## 附：一个被验证有效的设计

**预取未命中时，模型会自己补调 `search_knowledge`。**
20 题评测里 Q03（分红政策）就是如此 —— 预取的 5 个片段不够，模型主动追加检索。
这说明"预取保底 + 工具补充"这两条路并存的**分层设计是有效的**：
代码保证"一定有依据"，模型保留"不够时自己找"的灵活性。
